# 빈 자료함 정리 실패 분석

## 확인한 사실

- 작업 경로는 OneDrive 아래에 있다. 남아 있던 건물 폴더 3개에서 `ReadOnly, Directory, Archive, ReparsePoint` 속성을 확인했다. 실제 사용자 폴더의 속성이나 파일은 변경하지 않았다.
- 별도의 임시 폴더에 Windows 읽기 전용 속성을 설정하고 기존 방식의 `Files.delete`를 호출하자 `AccessDeniedException`이 재현됐다. 파일이 없어도 디렉터리 자체의 속성 때문에 실패할 수 있다.
- 기존 정리 코드는 한 번만 삭제를 시도하고 `getMessage()`만 출력했다. Windows에서는 메시지에 경로만 들어갈 수 있어 권한/속성 문제와 일시 점유를 구분하기 어려웠다.
- 파일 삭제는 실제 파일을 `data/.folder-trash`로 이동한다. 보관함은 건물 폴더 밖에 있으므로 그 파일이 건물 폴더를 비어 있지 않게 만드는 것은 아니다.
- 파일 작업 후 `reload()`가 목록을 비동기로 읽는다. 이 작업은 창 닫기와 시점이 겹칠 수 있다. 다만 목록 조회와 트리 조회의 스트림은 try-with-resources로 닫히며, 영구적인 핸들 누수는 발견하지 못했다. 별도 실험에서는 디렉터리 조회 핸들이 열린 상태에서도 삭제가 가능했다. 따라서 목록 조회 자체를 이번 실패의 확정 원인으로 보지 않는다.

## OneDrive 관련 판단

현재 속성과 경로는 OneDrive가 관여한 환경임을 보여주지만, 읽기 전용 속성을 어느 프로그램이 설정했는지 또는 과거 실패 순간 어떤 프로세스가 폴더를 점유했는지는 기존 출력만으로 판단할 수 없다. **읽기 전용 폴더 삭제 실패는 재현한 원인**, **OneDrive의 일시 점유·동기화 지연은 가능한 추가 원인**으로 구분한다. ReparsePoint 자체를 오류나 삭제 대상으로 취급하지 않는다.

Windows에서는 다른 핸들의 공유 모드가 삭제를 허용하는지에 따라 삭제 동작이 제한될 수 있다. Microsoft 문서: https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew

## 수정

1. 파일과 링크가 없는 폴더만 정리한다. 시간표 수업에 연결된 건물은 계속 보존한다.
2. 삭제 직전 폴더가 비어 있는지 다시 확인하고, Windows 읽기 전용 속성이 있는 경우 해당 빈 폴더에 한해 해제한다. 삭제에 실패하면 가능한 경우 원래 속성을 복원한다. 실제 파일은 강제로 삭제하지 않는다.
3. 실패하면 0.25초, 0.75초, 1.5초, 3초 간격으로 최대 4회 재시도한다. 재시도 전에 자료함 재열기·새 파일·시간표 연결 여부를 다시 확인한다. 프로그램을 닫으면 남은 재시도는 중단한다.
4. 닫힌 창의 대기 중 목록 조회는 건너뛴다. 파일 삭제의 실행 취소 정보는 빈 폴더가 정리돼도 현재 실행 동안 유지하며, 복구할 때 필요한 부모 폴더를 다시 만든다.
5. 실패와 재시도 결과는 `data/folder-cleanup.log`에 시간, 경로, 예외 클래스, Windows 오류 사유, DOS 속성과 함께 기록한다. 숨김 파일·링크가 있어 보존한 경우도 기록한다.

## 검증

OneDrive 작업 경로 아래의 별도 임시 폴더에서 읽기 전용 빈 하위 폴더 정리, 실제 파일 보존, 파일 생성·삭제 후 정리, 실행 취소 복구, 숨김 항목 보존, 자료함 밖 경로 거부를 확인했다. 이름 없는 건물 표시와 파일 검색창의 메인 창 중앙 배치는 Swing UI 검증으로 확인했다. Windows 네이티브 핸들로 디렉터리 삭제를 일시 차단한 뒤 잠금을 해제하는 시험에서도 자동 재시도, 최종 삭제 및 상세 로그 기록이 통과했다.

기존 사용자 폴더에 남은 데이터를 일괄 삭제하거나 OneDrive 설정을 변경하지 않았다. 과거 오류를 건별로 확정하려면 당시 상세 로그가 필요하며, 같은 문제가 재발하면 새 로그로 구분할 수 있다.
